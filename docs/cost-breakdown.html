What the 29 Cloud Functions actually cost

Across every function, trigger, and supporting service, the backend runs almost entirely inside Google's free tiers — a realistic $0/month recurring — the three Cloud Scheduler jobs sit exactly on the three-job free allowance — with a ceiling near $5. No function's compute is a lever. Two Google Maps Platform SKUs scale cost: Places autocomplete (bills per keystroke) and the Routes API the travel-time reminder sweep now calls (~13–16 calls per job as it approaches, ledger-capped once fired). Both sit under their 10K-free-per-SKU monthly caps at this business's volume (a busy 20-jobs/day month is ~9.6K Routes calls).

The one guardrail worth setting: a GCP Maps Platform billing alert covering both placesAutocomplete and the Routes API. Places' in-code rate limit became a real one on 2026-09-04 — it moved to the durable Firestore limiter, so 20/min per uid is now 20/min rather than up to ten times that across maxInstances containers — but it still fires once per keystroke while an address is typed, and an alert is what catches a run-away the cap does not; both Places proxies are admin-only (server-side assertAdmin), so only a trusted admin session can drive that spend. The trade is that address typing now costs one Firestore read and one write per lookup where it previously cost none — ~2,700 of each a month, well inside the free tier. The Routes API is called server-side by the leave-now sweep (never from the app) and is ledger-capped to fire once per job, so its spend scales only with job volume. The sweep also memoizes each drive-time estimate for ~10 minutes, so a job waiting out its 90-minute window is priced a couple of times rather than on all ~18 sweeps — a cached estimate can only defer a call, never trigger a send. The single alert backstops both APIs.

Two leaks closed on the reverse-geocode path (2026-09-01), found in production Crashlytics rather than in the numbers above. Node’s fetch() has no default timeout, so a slow upstream held the function open past the app’s own 10 s give-up: the client reported deadline-exceeded while the call kept running and still spent a billed Places call plus the rate-limit slot it had already consumed. All three Places callables now abort upstream at 8 s, under the client’s budget, so the server gives up first and no lookup is orphaned. On the app side a failed cell was not held, so every recycle of a live-map roster row re-requested it immediately against the 120/hour per-uid cap — ten staff failing together burned the hour’s budget and the whole map stopped resolving addresses. A failure is now held for five minutes before it may be retried. Neither changes steady-state volume; both remove spend that bought nothing. The fan-out itself is not fixed — N staff still issue N concurrent lookups when the map opens, and batching needs an endpoint that does not exist yet, so this stays the reverse-geocode line to watch.

  • Pricing: 2025 public Blaze-plan rates, us-central1 / North America. Rates change; treat as ballpark.
  • Scale modeled: 3 admins / 8 employees, ~700 clients, ~900 appointments/mo, ~50% needing a new address lookup, ~1.5 photos/appointment.
  • Free tiers cited: Functions 2M invocations + 180K vCPU-s; Places 10K calls per SKU; Firestore 50K reads / 20K writes / 20K deletes per day; Storage 5 GB; Scheduler 3 jobs (exactly three now run, so none bills); FCM push unlimited & free; Secret Manager 6 versions + 10K access.
