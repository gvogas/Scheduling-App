## 2. Deviations — do NOT "fix" these back

| Deviation | Why |
| --- | --- |
| **No invite email** (template, deep-link button, store fallback page). Codes stay shared out-of-band | Owner decision 2026-07-29. No email infrastructure exists and the provider choice is shared with the parked client-reminders work. |
| **12-character codes, three groups of four boxes** — not the spec's six | Existing codes are Crockford base32 `XXXX-XXXX-XXXX` (~60 bits); six characters is 30 bits. Not worth weakening for symmetry. Hash normalization already strips dashes and case. |
| **No "two tries left" counter, no "Keep me signed in", no "Use Face ID"** | Firebase Auth throttles opaquely and exposes no remaining-tries signal, so a client counter would lie; mobile sessions persist by default; biometric re-auth is deferred platform wiring, distinct from the app-lock that already ships. |
| **The invite banner shows role + expiry only — NOT the email** | Two reasons. `createEmployeeInvite` stamps no inviter identity, so "who invited you" has nothing to read; and the locked email panel sits directly beneath the banner, so the approved design would have printed the address twice on one short screen. Rendering it twice reads worse than either placement alone. |
| **`InvitePreview` lives in `features/employees/domain/models/`, not `features/auth/`** | The repository that returns it is the employees repository. Putting the model in `auth` would have made `employees` import `auth`, and the plan's own draft had the employees repo *throwing* `AuthFailure` — an import cycle plus a violation of the each-feature-throws-its-own-family rule. See trap 3. |
| **`previewInvite` errors are mapped in `AuthService`, not in the repository** | Exactly how `redeemSignupCode` is already layered: the repository lets `FirebaseFunctionsException` escape and the auth layer owns `AuthFailure`. Matching the shipped precedent beat matching the plan's prose. |
| **The field error message rides `InputDecoration.error`, not `errorText`** | `errorText` makes Material render its own error line, which printed the message a second time beside the design's red-dot row. `error` keeps the error border and the `AnimatedFormFieldWrapper` shake. |
| **`AuthScaffold` draws the lifted card only when a hero is present** | The reset-password *sent* state is hero-less by design and builds its own flat card. The alternative was a second flag on the scaffold, which would have changed how every other auth screen composes. |
| **`homeWidget` param and the `home_widget` tap channel both KEPT** | They retire together, later. Dropping the param while the channel is still a consumer re-breaks widget taps (`ios/CLAUDE.md`); dropping the channel is Mac-verification work P4b doesn't carry. The dispatcher skips `homeWidget` URIs instead. |
| **Tapping an invited roster row expands in place instead of opening the detail sheet** | An invited person has no jobs and no availability worth a detail page, and a re-issue refreshes their fields anyway. Owner decision 4. |
| **A revoked invite has no tombstone** | Revoke deletes the doc; the live stream drops the row. A "Revoked" state would need a new stored entity, which the program doc rejected. |
| **No new `PrimaryScrollScope`s** | Each auth screen owns exactly one scrollable on its own route, and the pending row lives inside the employees tab's already-scoped list. The hazard only exists for simultaneously-mounted scrollables. Consciously rejected, not overlooked. |
| **No Crockford aliasing (I→1, O→0) in the code boxes** | The generator never emits I/L/O/U, so aliasing would rescue a misread — but the server does none (`hashSignupCode` only uppercases and strips dashes), and a half-shared convention is worse than none. |

## 3. Bugs and traps found while building

1. **The baseline was not green on a fresh pull, and nothing about the failure said why.**
   `lib/l10n/.gen/` is gitignored, so a pull bringing new ARB keys leaves ~30 test files
   failing to **compile** ("loading [E]"), not failing assertions. `flutter gen-l10n` is the
   first thing a new session should run — see the banner at the top of this file.
2. **The plan's own `validateRedemption` refactor would have flipped a shipped precedence.**
   The shipped function checks **email-mismatch before expiry**. The plan's "pending-check
   then email-check" shape would make an expired-*and*-wrong-email code report `code-expired`
   instead of `code-email-mismatch` — undoing the distinction that exists precisely to kill the
   "invalid-code actually means the email doesn't match" confusion (see
   `feedback`/`project_signup_invalid_code_email_mismatch`). The shipped order is preserved,
   commented in `signup_code_utils.js`, and pinned by a jest case.
3. **The employees repository was throwing `AuthFailure`.** That broke the each-feature-throws-
   its-own-family rule, created an `employees → auth` import edge, and contradicted the
   precedent sitting right beside it — `redeemSignupCode` lets the raw
   `FirebaseFunctionsException` escape and `AuthService` maps it. Refactored so
   `AuthService.previewInvite` owns the mapping and `InvitePreview` stays in `employees`; the
   feature import edge stays one-way.
4. **`errorText` plus a custom red-dot row prints the message twice.** Material renders its own
   error line from `errorText`. Routing the message through `InputDecoration.error` instead
   keeps the red border and the shake without the duplicate line.
5. **`AnimatedCrossFade` keeps BOTH children built.** The first draft of the pending row used
   it, which left the revealed invite code in the tree — and reachable by a screen reader — on a
   *collapsed* row. That is a credential leak, not a layout nit. Replaced with `AnimatedSize`
   over a conditional child, so the collapsed body leaves the tree entirely.
6. **The invite banner and the locked email panel both wanted to show the address.** The
   approved design listed it in both; rendering it twice on one short screen reads worse than
   either. The banner shows role + expiry only.
7. **`awaitLoginRoute` must return a bool.** The plan's pseudocode awaited the wait and then
   pushed unconditionally — which pushes *after a timeout too*, reintroducing exactly the splash
   `pushReplacementNamed` race the wait exists to close. It returns whether `/login` actually
   arrived; a timeout leaves a breadcrumb and nothing else (the user still holds the code and
   can tap "Accept your invite" by hand).
8. **`TopRouteObserver` must NOT override `didRemove`.** `pushNamedAndRemoveUntil` pushes
   *before* it removes, so a `didRemove` override would overwrite the just-pushed name with a
   route no longer on the stack. The account-disabled path uses exactly that call.
9. **A re-issue silently wipes fields.** `performCreateInvite`'s re-issue branch *updates*
   `name`/`firstName`/`lastName`/`phone`/`colorValue`/`jobTitle`/`role` with whatever it is
   handed, so any re-issue call site passing blanks erases the invited person's phone and job
   title. `PendingInviteTile` threads every argument off the stored record, pinned by a test
   with **no `any()` matchers** on the wipeable fields.
10. **Expanding the row *is* the re-issue.** Option A has no "Show code" button, so the previous
    code dies the moment an admin opens the row to peek. Two things carry that honesty: the
    caption states the code is new **unconditionally** (when `codeExpiresAt` is present it reads
    "New code · expires {date}"; a pre-P4b invite has no stamp, so the dated line is omitted and
    a plain line still says the previous code no longer works), and the fetched code is cached
    in the tile's `State` **keyed by the invite doc id** so collapse → re-expand cannot re-mint.
    Without the cache, idly opening and closing a row burns the admin's shared 20/hour budget and
    rotates the code every time. Pinned by a test asserting exactly one repository call across an
    expand → collapse → expand cycle.
11. **The Task 9 sweep found a test-harness trap, not a layout bug.** `pumpWidget` reuses a
    `StatefulWidget`'s `State` across iterations of a scale loop, so the second iteration's tap
    *collapsed* an already-expanded row instead of opening it — the sweep silently stopped
    testing the expanded layout after the first scale. The tile is built with a fresh
    `UniqueKey()` per scale. Any future sweep that interacts with a stateful widget needs the
    same.
12. **iOS needed no change for `app_links`, and `FlutterDeepLinkingEnabled` staying `false` is
    correct.** The `esproschedule` scheme is already registered, and Flutter's own deep-link
    handler would otherwise consume the URL before `app_links` sees it.

## 4. Invariants established (now in `CLAUDE.md`)

1. **A displayed signup code is a credential** — widget/controller state and route args only;
   never logged (both auth catch sites go through `logger.authFailure`, whose breadcrumb carries
   the label and `failure.runtimeType` and nothing else), never persisted, never interpolated
   into a notice. The clipboard copy is the one sanctioned egress.
2. **The deep-link dispatcher is the single `app_links` consumer and MUST skip `homeWidget`
   URIs** (double-open); the param and the channel retire together, later. The invite branch
   pushes only once `/login` is the top route, `awaitLoginRoute` returns a bool, and
   `TopRouteObserver` has no `didRemove` override. A signed-in user gets an info notice, never
   an auto-sign-out.
3. **`codeExpiresAt` / `termsAcceptedAt` / `locationConsentAt` are function-owned** — on the
   `/users` update denylist, never in `EmployeeRecord.toMap()`; `redeemSignupCode` clears
   `codeExpiresAt` at activation and stamps the consent fields only when the payload flags are
   actually true.
4. **The invited-doc read matrix**: of the four `/users` read clauses only `isAdmin()` can reach
   an invited doc, so `codeExpiresAt` is admin-visible by construction. No read-rule change was
   needed or wanted.
5. **Invite re-issue refreshes the invited doc's editable fields** — every re-issue call site
   passes the stored record's current values, and expanding the row is a re-issue (hence the
   per-doc-id cache and the always-new caption).
6. The invited-employee-signup bullet was **updated, not replaced**: `CreateAccountScreen` is
   gone, the two-screen accept flow supersedes it, the profile fields and both consent flags
   ride `redeemSignupCode`, and `previewInvite` resolves the locked email.

Also corrected in `.claude/rules/error-handling.md`: it claimed intros **and** causes were
"lowercase mid-sentence fragments". Every shipped `error_intro*` key is **capitalized**
("Couldn't save the employee") because the intro is sentence-initial in
`"{intro} — {cause}. ({tag})"`; only the four causes are lowercase. New tags: `EMP-REVOKE`
(notice + log) and `DEEP-LINK` (log-only).

## 5. What P4b hands P5

- **Nothing structural.** P4b added no shared widget P5 must adopt and changed no convention P5
  inherits.
- **`isAvailabilityOnlyChange()` in `firestore.rules` is still uncalled** and still waiting for
  P5's self-service clause. `allow update` on `/users` remains admin-only. Don't delete it as
  dead rules code. A rules deploy still prints its three warnings (one `Unused function`, two
  `Invalid variable name`) — expected until P5 wires it, not a regression.
- **The `/users` update denylist now names four fields** (`uid`, `codeExpiresAt`,
  `termsAcceptedAt`, `locationConsentAt`). When P5 opens `allow update` to a user's own doc,
  that clause has to keep the denylist — a self-service edit must not be able to stamp its own
  consent record.
- **`allow create` on `/users` still has zero field validation** (the P5 spec's noted loophole).
  The three P4b timestamp caps are already written into `isValidUserData`, so when P5 wires that
  function into create they are correct rather than a fourth forgotten field family.
- **`TopRouteObserver` is now on `MaterialApp.navigatorObservers`** and is available to anything
  that needs to know the current top route name.

## 7. Deploy — ordering hazard, do not skip

`functions/invites.js`, `functions/signup_code_utils.js`, `functions/index.js` and
`firestore.rules` all changed. `firestore.indexes.json` did **not** —
`signupCodes.where("inviteDocId", "==", …)` is served by the single-field auto-index the
re-issue sweep already uses.

```bash
cd functions && npm run lint && npm test && cd ..
firebase deploy --only functions,firestore:rules,storage
```

**Never pass `--force`** — it deletes any prod Firestore TTL policy missing from
`firestore.indexes.json` (that removed all five live policies once, 2026-07-21). Omit
`firestore:indexes`. `storage` is the correct target, not `storage:rules`.

**The hazard, stated plainly:** the live `redeemSignupCode`'s `assertPayloadShape` allowlist is
still `new Set(["code"])` and **rejects unexpected keys**. The P4b client sends six. So from the
moment a build containing Task 2 ships, **every invite acceptance fails** with
`invalid-argument` — not degraded, not slower: no invited employee can join at all. The plan
deployed at Task 1 for exactly this reason; that deploy has not run.

> **Deploy `functions` before shipping any build containing Task 2, or ship both together.**

The reverse direction is safe, which is why the ordering is one-way: the widened callable
accepts the old `{code}` payload unchanged, `codeExpiresAt` is additive, `revokeInvite` and
`previewInvite` are simply uncalled by an older client, and the rules denylist blocks fields no
shipped client writes.

**This deploy also carries P4's still-pending backend** (P4 handoff §7 + §8e: the widened
`createEmployeeInvite`, the `emergencyPhone` rules cap, the withdrawn `/users` delete) — running
it closes that standing hazard too. Verify those land as well.

Post-deploy verification (do not skip): diff the deployed function list against `index.js`'s
exports — it should go from 21 live to **24** — re-fetch the live rules and confirm the four-field
update denylist, and check for ERROR-severity logs. The three `isAvailabilityOnlyChange`
warnings are expected.
