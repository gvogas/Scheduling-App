## 2. Deviations — do NOT "fix" these back

### 2.1 A client can never be removed (owner decision, 2026-08-01)

The plan shipped archive **and** kept the existing delete. The owner chose
neither, which also **withdrew a shipped feature**.

- **Why delete went:** deleting a client orphaned their history — past
  appointments keep the denormalized `clientName` but lose the `clientId` link.
- **Why archive never arrived:** it was the safe alternative, but it is what
  paid for the whole pagination rework. Archived docs must be filtered **in
  Dart** (pre-existing and Wave-imported docs have no `archived` field, and
  Firestore excludes docs missing a filter field). Filtering after the query
  shortens a page the server actually filled, which breaks the list's
  `items.length < pageSize` end-of-list test — one archived doc in a full page
  would truncate the list permanently.
- **Net effect on the code:** `fetchClientsPage` keeps its plain
  `Future<List<ClientRecord>>` and `_pageBoundaryNames` cursor exactly as they
  were pre-P3. `ClientPage`, `ClientCursor`, `hasMore`, `fetchArchivedClients`,
  `archivedClientsProvider`, `ClientListFilter`, `ClientsFilterBar` and
  `setArchived` were all built, then removed unbuilt-back. Do not resurrect any
  of them piecemeal.
- **The rule to remember:** if any future feature filters the clients page after
  the query returns, the page shape MUST change with it — a page object carrying
  the raw server-page size and a raw cursor. That is written up in CLAUDE.md.
- **Accepted cost, stated plainly:** the clients list and the booking picker now
  grow monotonically. A one-off customer stays in both forever. `deleteClient`
  is gone from the repository, the controller, the detail view and
  `firestore.rules` (`allow delete` withdrawn). The **Admin SDK bypasses rules**,
  so console/support cleanup still works.

### 2.2 Mobile consolidation replaces a migration

Owner change 5 removed `mobile` from the edit sheet. A removed field must not
strand a stored value, so `EditClientSheet._save` promotes `mobile` into `phone`
when `phone` is empty and clears `mobile` either way — on every save. The fleet
heals as clients are edited; there is no migration script and none is needed.
Pinned by three tests (`edit_client_sheet_test.dart`, group
`mobile consolidation`), one per row of the decision.

## 3. Bugs and traps found while building

1. **The scan-window patch's null branch was delete-only.** Removing delete left
   it unreachable. Restoring the testing delete brought the case back, so the
   method is now `_patchWindow(id, {data})` — one owner for the whole
   window/search-cache invalidation contract, with a null `data` meaning
   "dropped". An earlier revision had a second copy of it for the delete path;
   they drifted apart by construction and were merged.
2. **The l10n hook only fires on Edit/Write tool calls.** ARB edits made by
   script need a manual `flutter gen-l10n`. Bit this twice.
3. **`find.text('Save')` is ambiguous on the client detail.** The read-only body
   carries a "Save to contacts" tile whose label also renders `Save`, behind the
   edit sheet. Tests scope it via `find.descendant(of: find.byType(EditClientSheet), …)`.
4. **`ListItemTile.subtitle` is single-line by contract**, so the chip row needed
   a new general `subtitleExtra` slot rather than a `Column` crammed into
   `subtitle`. P4's team rows will want the same slot.
5. **`clients_saveToContacts` was literally `"Save"`.** Fine as a tile beside
   Call/Directions; misleading as a standalone row on a read-only page, where it
   reads as "save changes". Relabelled to "Save to contacts" / "Enregistrer aux
   contacts" — one call site, no other consumer.
6. **A stale root-level `test/client_tile_test.dart`** duplicated the feature-scoped
   tile test and asserted the phone was the subtitle. Corrected in place rather
   than deleted — its tap / avatar / overflow cases are still unique coverage.

## 4. Invariants established (now in CLAUDE.md)

- A client is never removed — no delete, no archive; and *why* the pagination
  shape depends on that staying true. Temporarily reopened by the debug-gated
  testing delete — see §5b, which must be swept before submission.
- `jobCount` is recomputed absolutely, never incremented (`retry: true` would
  double-count), fires only when `clientId` changes, and writes with `update()`
  so a client removed out-of-band is never resurrected as a count-only stub.
- `toMap` must never emit `waveCustomerId` / `wave` / **`jobCount`**.
- `mobile` self-heals into `phone` on every edit save.
- The type filter is a separate bounded read, never a filter over the paginated
  list — same reasoning as the archive decision, and the reason it was safe to
  build when archive was not.

## 5b. PRE-SHIP REMOVAL CHECKLIST — do not ship without doing this

> **STATUS 2026-08-01: the rules half of this is LIVE IN PRODUCTION.**
> `allow delete: if isAdmin();` on `/clients` went out with the deploy below,
> with owner approval after the exposure was flagged. Until step 2 is done and
> rules are redeployed, **any admin session can permanently delete a client
> doc**, which orphans that client's past appointments (they keep the
> denormalized `clientName` and lose the `clientId` link). The `kDebugMode` gate
> does not help here — see the note at the end of this section.

A temporary client delete was added 2026-08-01 so junk test data can be cleared.
Shipping behaviour is still that **a client is never removed**. Everything is
marked `TODO(george): ... (#pre-ship)`; `grep -rn "#pre-ship" lib/ firestore.rules`
finds all of it. To remove:

1. Delete `lib/core/testing_flags.dart`.
2. Delete `allow delete` from `/clients/{clientId}` in `firestore.rules` **and
   redeploy rules**. This is the one that matters: rules are not build-aware, so
   that hole is open in production the whole time the line is there, regardless
   of the debug gate.
3. Remove `deleteClient` from `ClientsRepository`, `FirebaseClientsRepository`
   and `ClientFormController` (plus `ClientDeleteOutcome`). The cache patch it
   calls (`_patchWindow`) is shared with the add/edit path — keep it, just drop
   the delete's call.
4. Remove `_confirmTestingDelete`, the gated button and `onDeleted` from
   `client_detail_view.dart`, and the `onDeleted:` arguments in
   `clients_screen.dart` and `client_detail_sheet.dart`.
5. Delete the two tests named "deleteClient (testing-only)" / "the only delete
   is the debug-gated testing one". No ARB sweep is needed — every string on
   this path is an inline literal inside the gated code.

**The button is debug-only** (`kShowTestingDeleteClient = kDebugMode`), so the
*UI* cannot reach the App Store even if this checklist is missed. **The rules
hole is a separate matter and the debug gate does not cover it** — rules are
deployed server-side and know nothing about build mode, so the delete stays
permitted for any admin credential (including a scripted SDK client) for as long
as the line is live, no matter what the app binary does. Step 2 is the one that
actually closes it. TestFlight and App Distribution builds are release mode and
will NOT show the button; flip the constant to `true` if you need it there, and
flip it back.
