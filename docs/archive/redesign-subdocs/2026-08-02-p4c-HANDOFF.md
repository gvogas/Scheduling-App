## 1. What this replaces, and why

**Owner decision, 2026-08-02.** The P4b one-time signup code flow is withdrawn entirely — along
with the invite email and the static landing page that were explored earlier the same day. The new
model:

1. Admin fills the person sheet → `createEmployeeAccount` mints a **Firebase Auth account** with
   the shared starting password **`Welcome123!`** and a `users` doc that is `invited` but already
   carries the real `uid`.
2. Admin reads the email + password off the dialog (or off the expanded roster row later) and
   hands them over out-of-band.
3. Employee signs in normally. The app sees `status == 'invited'` and routes them to
   `AccountSetupScreen` instead of the hub.
4. They set their own password and fill in name/phone/consent → `completeEmployeeSetup` flips the
   doc to `active`.

**The security posture, stated plainly, because it is weaker than what it replaced.** `Welcome123!`
is known to everyone forever. Between account creation and first sign-in, anyone who knows an
employee's email can sign in as them and complete setup. The old 12-character random code was
~60 bits of entropy protecting exactly that window. What holds now instead:

- The account stays `invited` until setup completes, and `firestore.rules` grants an `invited`
  user **nothing** — no clients, no appointments, no peers. The window is "can reach the setup
  screen as this person", not "can read the business".
- **The window is under the admin's control.** Create the account when you are handing the
  credentials over, not weeks ahead. This is the actual mitigation and it is operational, not
  technical. It belongs in whatever onboarding instructions you write.

This was raised before building and the owner proceeded. It is recorded here so nobody
re-discovers it as a surprise.

## 4. Decisions worth not re-litigating

| Decision | Why |
| --- | --- |
| **The Auth account is minted up front**, so the `users` doc carries `uid` from creation | It is what lets an `invited` person read their own doc on the setup screen — and it let a whole `/users` read clause be deleted (the old `email_verified && invited && email == token.email` clause existed only because the code flow left `uid` empty until redemption). |
| **Password change happens BEFORE activation, client-side** | The server cannot see a password. "You must replace the shared default" is true only because `completeEmployeeSetup` is unreachable until `updatePassword` succeeds. Swap the order and an interrupted setup leaves an *active* account still on `Welcome123!`. Pinned by a test. |
| **A failed activation does NOT revert the password** | The new password is the one the person just chose and typed twice. Leaving them `invited` with a working password beats resetting them to the shared default. Next sign-in routes back to setup, which never assumes the current password is the default. |
| **Re-running create on a still-`invited` person resets their password** | That IS the "they never signed in / they lost it" path, so password reset comes for free. It refuses once someone has set up — checked *before* touching Auth, so it can never reset a real person's chosen password and only then discover Firestore says no. |
| **`deleteEmployeeAccount` only works while `invited`** | Once someone sets up, the existing no-delete invariant applies and disable is the only removal. Transactional, so a setup that commits first makes the delete refuse. |
| **Provisioning rolls back** | If the Firestore write fails after the Auth account is created, the Auth account is deleted — but only if *we* just minted it. An Auth account with no `users` doc is a sign-in `SplashScreen` can't resolve and no admin surface can see. |
| **`kDefaultStartingPassword` is hand-mirrored in Dart** | Only ever a display fallback for a row whose account was created earlier. Any surface that just called the callable shows the password the **server echoed back**, so a drift can't reach the screen where it matters. Both sides carry a pointer to the other. |
| **The "Accept your invite" prompt is gone from sign-in** | There is nothing left to accept. |
| **An old `esproschedule://invite?code=…` link now falls through to `IgnoredLink`** | Those links can still be in someone's messages; they must not reach a screen that no longer exists. |

## 5. Production data migration — REQUIRED, not optional

**Every existing `invited` users doc in production is now unusable.** They were created by the old
flow, so they have `uid: ""` and no Firebase Auth account — the new sign-in path has nothing for
them to sign in *with*, and `deleteEmployeeAccount` will happily remove them but nothing will
recreate them.

Before or immediately after the deploy, for each pending invite:

1. List them: `users` where `status == 'invited'` (admin console or Admin SDK).
2. Either delete each one and re-create the person through the new flow, or run a one-off Admin
   SDK script that mints the Auth account and patches `uid` onto the existing doc.

Also drop the now-orphaned `signupCodes` collection — no code reads it any more, and its rules
block is gone, but the documents are still sitting there. The Firestore **TTL policy** on
`signupCodes.expiresAt` should be removed from the console too, and its `fieldOverrides` entry from
`firestore.indexes.json` if one exists (check before deploying `firestore:indexes` — see the
never-`--force` rule).

## 7. Deploy — the ordering hazard is now two-way

This is **sharper than P4b's**, which was one-way safe. Here neither direction is:

- `firebase deploy --only functions` **deletes** `createEmployeeInvite`, `redeemSignupCode`,
  `revokeInvite` and `previewInvite`. The CLI will prompt for the deletions — that is expected, not
  a mistake. **Any already-installed build immediately loses invite acceptance and employee
  creation.**
- The new client calls `createEmployeeAccount` / `completeEmployeeSetup` /
  `deleteEmployeeAccount`, which do not exist until this deploys. **A build shipped before the
  deploy cannot create an employee at all.**

> **Ship the app build and the backend together. There is no safe interleaving.**

```bash
cd functions && npm run lint && npm test && cd ..
firebase deploy --only functions,firestore:rules,storage
```

**Never pass `--force`** — it deletes any prod Firestore TTL policy missing from
`firestore.indexes.json` (that removed all five live policies once, 2026-07-21).

**`firestore.indexes.json` HAS now been deliberately edited**: the `signupCodes` `expiresAt`
`fieldOverride` was removed (§5), so adding `firestore:indexes` to the deploy is what retires that
TTL policy. Every other policy is still declared, so the drift-deletion behaviour will remove
exactly the one intended. Deploy it in the same run *or* leave it off and drop the policy by hand
in the console — but don't leave the file edited and then wonder why the console still lists it.

Post-deploy: the live function list should go **24 → 23**; confirm the three-field `/users` update
denylist in the deployed rules; check for ERROR-severity logs. The three
`isAvailabilityOnlyChange` warnings are still expected (P5 has not wired it).

**This deploy still also carries P4's and P4b's pending backend** (P4 §7/§8e, P4b §7) — those never
ran either. Verify they land.
